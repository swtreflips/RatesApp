2. WHEN TO CONNECT SUPABASE — RECOMMENDED TIMELINE
________________________________________________________________________________

The answer is: create the Supabase project and tables NOW, but connect
features to it incrementally. Here's why and how:


  PHASE A — Supabase Project Setup (do immediately, before more UI work)
  -----------------------------------------------------------------------

  Why now:
    - rateRequestService.js is already calling supabase.from(). If you keep
      building more UI without a real database, you'll accumulate "fake"
      patterns that need to be ripped out later.
    - The longer you wait, the more components you build with hardcoded
      placeholder data ("—" in stat cards), making the retrofit larger.
    - Setting up tables early lets you validate your data model assumptions
      while the codebase is small and easy to change.

  What to do:
    1. Create a Supabase project (free tier is fine for dev)
    2. Create the tables from the schema in rateRequestService.js
    3. Add a .env.local file with VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY
    4. Add .env.local to .gitignore (it isn't tracked now)
    5. Verify the "Post Batch" flow actually inserts data
    6. Create a SQL migrations file or use Supabase dashboard — but
       document the schema somewhere reproducible

  PHASE B — Wire Requester Read Flows (after Phase A, before Provider)
  -----------------------------------------------------------------------

  Once tables exist and inserts work, build the read side:
    - "My Requests" page: fetch batches for the current user
    - Dashboard stat cards: count queries against real data
    - Batch detail view: show lanes within a batch
    - Status display on batches

  This is the natural moment because you already have the write path.
  Building reads immediately after writes keeps the feedback loop tight.


  PHASE C — Auth Flow (before opening Provider domain)
  -----------------------------------------------------------------------

  Before building the provider side, you need real auth because:
    - Providers and requesters must be different users
    - You need requester_id on batches to be a real user UUID
    - Provider submissions must know which provider submitted them
    - The dev role toggle won't work for testing two-role workflows

  What to do:
    - Build a login/signup page
    - Add a profiles table or user_metadata setup for role assignment
    - Add route guards (redirect unauthenticated users to login)
    - Keep the dev toggle as a fallback but behind an env flag


  PHASE D — Provider Domain + Quotes Table (Phase 3 in your roadmap)
  -----------------------------------------------------------------------

  Build provider features against real data from day one. The provider
  sees the same lane_requests the requester created — this is the
  "one dataset, different views" principle from CLAUDE.md.

  New table needed: provider_quotes / rate_submissions
  New queries: fetch open lanes, submit a quote, view my submissions

3. ISSUES AND GAPS IN THE CURRENT CODEBASE
________________________________________________________________________________

  3.1  NO DATA FETCHING LAYER / HOOKS
  ------------------------------------
  Current state: rateRequestService.js has a write function, but there are
  no read functions and no React hooks for data fetching.

  Problem: Every page that needs data (dashboards, "My Requests", provider
  lanes) will need to fetch from Supabase. Without a pattern established,
  each page will invent its own approach.

  Recommendation: Before building more pages, establish a data hook pattern.
  Two options:

    Option A (lightweight): Custom hooks per feature
      e.g., features/requester/hooks/useBatches.js
      Uses useState + useEffect + supabase queries internally.

    Option B (recommended): Add React Query (@tanstack/react-query)
      Gives you caching, background refetching, loading/error states,
      and stale-while-revalidate out of the box.
      This is almost always worth the small dependency for apps that
      do significant data fetching.

  Why this matters now: The dashboard stat cards are hardcoded to "—".
  The "My Requests" page is a placeholder. Both need data. If you add
  React Query now, every future page gets the pattern for free.


  3.2  INCOMPLETE DATA MODEL
  ---------------------------
  The schema in rateRequestService.js defines only two tables:
    - rate_request_batches (id, requester_id, created_at, status)
    - rate_request_lanes (id, batch_id, pol, fd, created_at)

  Missing tables/columns you will need:

    profiles (or use auth.users metadata):
      - id (FK to auth.users)
      - role (requester | provider)
      - company_name
      - created_at

    rate_request_lanes (additional columns):
      - status (open | quoted | awarded | closed)
      - container_type (20GP, 40GP, 40HC, etc.)
      - commodity
      - volume / quantity
      - valid_from / valid_to dates
      - notes / special_requirements

    provider_quotes:
      - id
      - lane_id (FK to rate_request_lanes)
      - provider_id (FK to auth.users)
      - rate_amount (numeric)
      - currency
      - transit_time_days
      - valid_until
      - notes
      - status (submitted | accepted | rejected | expired)
      - created_at

    (future) provider_coverage:
      - provider_id
      - region / port / trade_lane filters
      Used for the coverage/filtering concept mentioned in CLAUDE.md

  Recommendation: You don't need to build all these tables today, but
  you SHOULD design the full schema on paper before creating the first
  tables. Changing Supabase tables after data exists is harder than
  getting the schema right up front.


  3.3  LANE DATA IS TOO SIMPLE
  -----------------------------
  Currently a lane is just { pol, fd } — port of loading and final
  destination. For an ocean freight rate request platform, this is
  insufficient for providers to submit meaningful quotes.

  At minimum, providers will need to know:
    - Container type (critical — rates differ hugely between 20GP and 40HC)
    - Commodity type (affects pricing, especially for hazmat/reefer)
    - Expected volume
    - Validity period (rates expire)
    - Incoterms or service type (port-to-port vs door-to-door)

  Recommendation: Expand the NewRateRequest grid columns BEFORE connecting
  to Supabase, so the table schema matches from the start. Adding columns
  to both the DataGrid and the database table simultaneously is cleaner
  than retrofitting later.


  3.4  NO ERROR BOUNDARIES FOR SUPABASE FAILURES
  ------------------------------------------------
  Current state: supabase.js logs a console.warn if env vars are missing,
  then creates a client with placeholder URLs. AuthProvider catches the
  getSession error silently. rateRequestService.js returns errors in the
  response object.

  Problem: When Supabase is unreachable (network issue, wrong credentials,
  project paused), the app will fail silently or show confusing errors.
  The "Post Batch" button will fail with an opaque error.

  Recommendation:
    - Add a connection health check on app init
    - Show a clear banner when running in offline/dev-mock mode
    - Consider a "Supabase not configured" state in the UI vs silent failure


  3.5  NO .env.example FILE
  --------------------------
  There's no .env.example or documentation of required environment
  variables. Anyone cloning the repo won't know what to configure.

  Recommendation: Add a .env.example with:
    VITE_SUPABASE_URL=https://your-project.supabase.co
    VITE_SUPABASE_ANON_KEY=your-anon-key


  3.6  MODULE-LEVEL MUTABLE STATE (nextId)
  ------------------------------------------
  In NewRateRequest.jsx, `let nextId = 1` is a module-level counter for
  generating temporary row IDs in the DataGrid.

  This works fine for the local grid (temporary IDs before saving), but
  be aware:
    - These IDs are not stable across page navigations
    - Once data comes from Supabase, rows will have real UUIDs
    - The DataGrid's `id` field will need to handle both temp IDs (for
      new unsaved rows) and real UUIDs (for fetched/saved rows)

  Recommendation: When you integrate Supabase reads, adopt a pattern like:
    - Temp rows use `temp-{counter}` string IDs
    - Saved rows use their Supabase UUID
    - The service layer knows to insert rows without a UUID and update
      rows that have one


  3.7  NO NAVIGATION AFTER SUCCESSFUL POST
  ------------------------------------------
  After "Post Batch" succeeds, the component resets rows to empty but
  stays on the same page. The user has no way to see the batch they
  just created.

  Recommendation: After a successful post, navigate to a batch detail
  page or to "My Requests" so the user can confirm their data was saved.
  This also validates that the read flow works end-to-end.


  3.8  MISSING LOADING / EMPTY STATES FOR DATA PAGES
  ----------------------------------------------------
  The RequesterDashboard and ProviderDashboard have placeholder stat
  values and a PlaceholderPage for "No requests yet." Once connected
  to Supabase, these need three states:
    - Loading (spinner or skeleton)
    - Empty (no data yet — call to action)
    - Populated (real data displayed)

  This is a common pattern that should be standardized in a shared
  component or hook before building multiple data-driven pages.


  3.9  NO REAL-TIME SUBSCRIPTIONS
  --------------------------------
  For a two-role platform where providers need to see new lane requests
  as they're posted, Supabase Realtime is a natural fit.

  Not needed immediately, but design the data fetching hooks so that
  adding a realtime subscription later is a small change (e.g., the hook
  can accept a { realtime: true } option that adds a supabase
  .channel() listener alongside the initial fetch).


  3.10  SIDEBAR NAVIGATION AND ROUTES ARE IN SYNC — GOOD
  --------------------------------------------------------
  The Sidebar nav items match the routes in RequesterRoot and ProviderRoot.
  This is well done. Keep this pattern as you add more routes.


  3.11  AUTH ROUTE GUARDS DON'T EXIST YET
  -----------------------------------------
  Currently any role can navigate to any route manually (e.g., a provider
  could type /requester/new in the URL bar). RoleRouter redirects based
  on role at "/", but doesn't block cross-role access.

  Recommendation: Add route guards before going to production. This can
  be simple — a wrapper component that checks role and redirects if
  mismatched.

5. STATE MANAGEMENT RECOMMENDATIONS
________________________________________________________________________________

  Current approach: Local component state only (useState).

  This is fine for Phase 1 shell + simple forms. But as data-driven
  pages multiply, you'll need:

  RECOMMENDED STACK:
    - React Query for server state (Supabase data)
    - React Context for global client state (auth, role, theme)
    - Local state for ephemeral UI state (form inputs, open/close toggles)

  DO NOT over-engineer:
    - You do NOT need Redux, Zustand, or Jotai for this app size
    - React Query + Context covers your needs entirely
    - Keep it simple: each feature domain fetches its own data through
      hooks that use React Query under the hood

  PATTERN TO ESTABLISH:
    features/requester/hooks/useBatches.js
      -> uses useQuery() to fetch from supabase
      -> returns { batches, isLoading, error }

    features/requester/hooks/usePostBatch.js
      -> uses useMutation() to insert via supabase
      -> returns { postBatch, isPosting, error }
      -> invalidates the batches query on success

  This replaces the manual useState + async function pattern in
  NewRateRequest.jsx with something that handles caching, refetching,
  and loading states automatically.
