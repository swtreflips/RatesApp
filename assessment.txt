================================================================================
  PART 1: PROJECT STRUCTURE
================================================================================


────────────────────────────────────────────────────────────────────────────────
  WHAT'S CLEAN
────────────────────────────────────────────────────────────────────────────────

  1. FEATURE DOMAIN SEPARATION

    src/features/requester/ and src/features/provider/ are isolated.
    Each has its own pages/, services/, and (future) hooks/ and
    components/ directories. This matches the CLAUDE.md philosophy:
    "separate feature modules inside one codebase."

    This pattern holds. You can add a third role (admin, analyst)
    by adding src/features/admin/ without touching existing code.

  2. SHARED SHELL IS ROLE-AGNOSTIC

    Shell.jsx has no idea what a rate request is. It mounts Sidebar,
    TopNav, and RoleRouter. All role-specific logic lives in the
    feature domains. This is correct — the shell is a container,
    not a business layer.

  3. SINGLE AUTH CONTEXT

    AuthProvider is the one place that knows about session, user,
    and role. Every component that needs identity calls useAuth().
    No prop drilling, no duplicate auth checks. Clean.

  4. ROLEROUTER CENTRALIZES ACCESS

    Route mounting is conditional on role. One file controls who
    sees what. Adding new routes means editing RequesterRoot or
    ProviderRoot — not touching the shell or auth layer.

  5. DOCUMENTATION ALONGSIDE CODE

    The .txt planning docs (data model, lifecycle, testing plan)
    live in the project root. They serve as living specs. This is
    unusual but practical for a project where one person builds
    and the design evolves through conversation.


────────────────────────────────────────────────────────────────────────────────
  WHAT'S MISSING
────────────────────────────────────────────────────────────────────────────────

  1. NO src/hooks/ DIRECTORY

    CLAUDE.md specifies a hooks/ folder for shared hooks. You have
    useIsMobile in Shell.jsx (inline) and useAuth in AuthProvider.
    As you add more (useSupabaseQuery, useToast, useLanes), they
    need a home.

    Create: src/hooks/
    Move useIsMobile there. It's already generic.

  2. NO src/components/ BEYOND SHELL

    src/components/shell/ exists. But there's no src/components/
    for shared non-shell UI: toast component, confirmation modal,
    status badges, data table wrappers. These will be needed across
    both requester and provider domains.

    The PlaceholderPage is in components/shell/ but it's used by
    features, not by the shell. It belongs in src/components/.

  3. NO CONSTANTS FILE

    Magic strings are scattered:
      - Roles: 'requester', 'provider' (AuthProvider, RoleRouter, Sidebar)
      - Container types: ['20GP', '40GP', '40HC', ...] (NewRateRequest)
      - Statuses: 'posted' (rateRequestService)
      - TTL duration: 14 days (LANE_LIFECYCLE doc, not in code yet)

    Create: src/lib/constants.js
    Centralize these. When you change a container type list or add
    a role, you change one file instead of hunting across components.

  4. NO ERROR BOUNDARY

    If NewRateRequest throws (bad DataGrid state, Supabase crash),
    the entire app white-screens. React error boundaries catch
    component-level errors and show a fallback UI.

    Add one wrapping RoleRouter in Shell.jsx. Simple:
      <ErrorBoundary fallback={<ErrorPage />}>
        <RoleRouter />
      </ErrorBoundary>

    This prevents a single feature crash from killing the whole app.

  5. NO TYPES OR SCHEMAS

    You have @types/react and @types/react-dom installed (devDeps)
    but the project is plain JavaScript. That's fine for now, but
    as the data model grows (lanes, rates, batches, providers,
    periods), you'll lose track of what shape objects have.

    You don't need full TypeScript migration. Consider JSDoc type
    annotations in service files at minimum. They give IDE autocomple
    without changing the build.


────────────────────────────────────────────────────────────────────────────────
  WHAT NEEDS REORGANIZING
────────────────────────────────────────────────────────────────────────────────

  1. TOAST IS EMBEDDED IN NEWRATEREQUEST

    The toast (lines 33-37, 260-271 in NewRateRequest.jsx) is a
    component-level implementation. When you build "My Requests",
    "Received Rates", provider pages — each will need toasts too.

    Extract to: src/components/Toast.jsx + src/hooks/useToast.js
    Or use a context-based toast provider (like AuthProvider but

  2. useIsMobile IS TRAPPED IN Shell.jsx

    This hook is generic and reusable. NewRateRequest might need
    it to adjust DataGrid column widths. Provider pages might
    need it for responsive layouts.

    Move to: src/hooks/useIsMobile.js

  3. PlaceholderPage LOCATION

    It's in src/components/shell/ but it's used by feature pages
    (RequesterRoot, ProviderRoot). It's not a shell component —
    it's a shared UI utility.

    Move to: src/components/PlaceholderPage.jsx


================================================================================
  PART 2: SCALABILITY
================================================================================


────────────────────────────────────────────────────────────────────────────────
  WILL CURRENT PATTERNS HOLD AS FEATURES MULTIPLY?
────────────────────────────────────────────────────────────────────────────────

  ROUTING — YES, IT SCALES

    Current: RoleRouter → RequesterRoot → child routes
    Adding pages means adding <Route> entries in RequesterRoot or
    ProviderRoot. The shell doesn't change. This is the correct
    pattern for 5, 15, or 50 pages.

    Potential issue at scale: If RequesterRoot grows past ~15 routes,
    consider lazy loading with React.lazy() and Suspense. Not needed
    now, but keep it in mind.


  FEATURE ISOLATION — YES, IT SCALES

    Each feature domain is self-contained. A requester feature can
    have its own hooks, services, components, and pages without
    affecting the provider domain. This is the core strength of
    the architecture.


  STATE MANAGEMENT — NO, THIS NEEDS ATTENTION

    Current state approach: useState inside each component.
    This works for NewRateRequest (local form state) but will NOT
    work for:

      - Dashboard stats: need to fetch counts from Supabase
      - My Requests page: fetch + display + paginate lane lists
      - Received Rates: fetch rates, group, filter, sort
      - Provider Open Lanes: fetch active lanes, real-time updates
      - Provider Submissions: fetch submission history

    Every one of these pages needs: loading state, error state,
    data state, refetch capability, caching.

    If you build each one with raw useState + useEffect + supabase
    queries, you'll repeat the same fetch/loading/error boilerplate
    in every component. And you'll have no caching — navigating
    away and back re-fetches everything.

    THE FIX: Install @tanstack/react-query (React Query).
    One dependency. Gives you:
      - Automatic loading/error states
      - Caching (navigate away and back = instant)
      - Background refetching (data stays fresh)
      - Mutation handling (post, then auto-refresh lists)
      - Pagination support

    This is the single most impactful thing you can add before
    building more data-driven pages.


  SERVICE LAYER — PARTIALLY SCALES

    rateRequestService.js is the right pattern: a file that exports
    functions wrapping Supabase queries. But it only has ONE function
    (postRateRequestBatch). As you build out features, you'll need:

      - fetchBatches(requesterId)
      - fetchLanesByBatch(batchId)
      - fetchActiveLanes()
      - fetchRatesForLane(laneId, period)
      - submitRate(laneId, rateData)
      - extendLane(laneId)
      - fetchDashboardStats(userId, role)

    These should live in feature-specific service files:
      src/features/requester/services/laneService.js
      src/features/requester/services/rateService.js
      src/features/provider/services/laneService.js
      src/features/provider/services/submissionService.js

    Or in a shared service if both roles query the same table:
      src/lib/services/laneService.js
      src/lib/services/rateService.js

    The current pattern (service file → export async functions →
    call supabase) is correct. Just plan for multiple service files
    per feature domain.


  COMPONENT REUSE — NEEDS A SHARED LAYER

    Right now the only shared components are in src/components/shell/.
    But upcoming features will need shared UI across both domains:

      - DataGrid wrapper (standardized column configs, styling)
      - Status badges (Active, Pending, Expired)
      - Lane summary card
      - Rate comparison table
      - Confirmation modal
      - Empty state component
      - Loading skeleton

    Without a shared component library, you'll duplicate these
    between requester and provider. Put them in src/components/.


────────────────────────────────────────────────────────────────────────────────
  THE SUPABASE SCHEMA VS. THE CODE
────────────────────────────────────────────────────────────────────────────────

  Your documentation describes a rich data model:
    - Lanes with TTL, periods, expires_at, posted_at
    - Rates with pod, last_cy, carrier, rate_amount, period
    - Competitive bidding with append-only rate history
    - Lane extension resetting the current period

  Your code currently has:
    - rate_request_batches (id, requester_id, status, created_at)
    - rate_request_lanes (id, batch_id, pol, fd, created_at)
    - The service inserts pol and fd only

  The gap is significant. The DataGrid now captures containerType
  and containerCount, but the service layer doesn't send them to
  the database (the table schema doesn't have those columns yet).

  This isn't a code problem — it's a sequencing problem. The data
  model in your docs is ahead of what the code and database support.
  When you create the Supabase tables, build them to match the full
  LANE_LIFECYCLE model, not the minimal schema in rateRequestService.

  MISMATCH TO FIX: rateRequestService.js maps { pol, fd } to the
  database insert. The handlePost in NewRateRequest now sends
  { pol, fd, containerType, containerCount } but the service
  layer ignores containerType and containerCount. The laneRows
  mapping (rateRequestService.js line 39-43) only spreads pol
  and fd. This will silently drop the new fields.

────────────────────────────────────────────────────────────────────────────────
  WHAT YOU HAVE AND WHETHER IT'S RIGHT
────────────────────────────────────────────────────────────────────────────────

  REACT 18 — CORRECT
    Stable, well-supported. No reason to move to 19 yet. Works with
    all your dependencies.

  VITE — CORRECT
    Fast dev server, fast builds. Right choice for a React SPA.
    No config bloat (your vite.config.js is 7 lines).

  REACT ROUTER v7 — CORRECT
    Feature-rich routing, supports nested routes which you use.
    The pattern of RequesterRoot/ProviderRoot as nested route
    containers is idiomatic.

  TAILWIND CSS 3 — CORRECT
    Utility-first works well for this project. Your components are
    consistently styled with Tailwind. The custom brand palette in
    tailwind.config.js is the right approach for theming.

  SUPABASE JS — CORRECT
    Matches your architecture (no custom backend, browser-direct
    queries). The client setup in lib/supabase.js is minimal
    and correct.

  MUI X DATAGRID — CORRECT, WITH CAVEATS
    The DataGrid is the right tool for editable lane/rate grids.
    No Tailwind-only alternative offers inline editing, column
    types (singleSelect, number), and CSV-like UX.

    CAVEAT: @mui/material (the base library) is a large dependency
    that ships MUI's entire component system. You only use it
    because DataGrid requires it as a peer dependency. You no
    longer import any @mui/material components directly (good —
    you removed MUI Button/Stack/Snackbar in favor of Tailwind).

    Consider: When DataGrid releases a standalone version without
    the @mui/material peer dep, switch to it. Until then, this
    is an acceptable cost.

  @EMOTION/REACT + @EMOTION/STYLED — NECESSARY OVERHEAD
    These exist solely because MUI requires them. You don't use
    Emotion directly. No action needed — they come with MUI.

  LUCIDE-REACT — CORRECT
    Lightweight, consistent style, tree-shakeable. You've
    standardized on it after removing @mui/icons-material. Good.

  PAPAPARSE — CORRECT
    Purpose-built CSV parser. Small, well-maintained. Used only
    in NewRateRequest for CSV upload. Correct choice.


────────────────────────────────────────────────────────────────────────────────
  WHAT'S MISSING
────────────────────────────────────────────────────────────────────────────────

  @TANSTACK/REACT-QUERY — SHOULD ADD

    As discussed in the scalability section. This is the #1 missing
    dependency. Every data-fetching page you build will be simpler
    and more robust with React Query.

    Install: npm install @tanstack/react-query
    Add QueryClientProvider in App.jsx (next to AuthProvider).
    Then each feature writes hooks like:

      function useLanes() {
        return useQuery({
          queryKey: ['lanes', 'active'],
          queryFn: () => supabase.from('rate_request_lanes')
            .select('*')
            .gt('expires_at', new Date().toISOString()),
        })
      }

    Returns { data, isLoading, error } automatically.


  NO FORM LIBRARY — ACCEPTABLE FOR NOW

    NewRateRequest uses DataGrid for input, not a traditional form.
    You don't need React Hook Form or Formik unless you build
    complex standalone forms (settings, profile, provider rate
    submission outside a grid). Wait and see.


  NO TEST FRAMEWORK — LOW PRIORITY BUT FLAGGED

    No test files exist. No vitest, jest, or testing-library in
    dependencies. For a project in active prototyping, this is
    acceptable. But before going to production with real freight
    forwarders, add:

      npm install -D vitest @testing-library/react @testing-library/jest-dom

    Priority tests: service functions (rateRequestService) and
    data transformation logic (dedup, laneKey).


────────────────────────────────────────────────────────────────────────────────
  WHAT'S OVERKILL OR UNUSED
────────────────────────────────────────────────────────────────────────────────

  @TYPES/REACT + @TYPES/REACT-DOM

    Installed as devDependencies but you write .jsx not .tsx.
    These do nothing in a JavaScript project. They don't hurt
    (tiny, dev-only), but they suggest a TypeScript setup that
    never happened. Remove them if it bugs you, or leave them
    as a breadcrumb for future TS migration.


================================================================================
  PART 4: DATA FLOW
================================================================================


────────────────────────────────────────────────────────────────────────────────
  CURRENT DATA FLOW
────────────────────────────────────────────────────────────────────────────────

  The app currently has ONE data write path and ZERO data read paths:

  WRITE (NewRateRequest → rateRequestService → Supabase):

    User adds rows in DataGrid
      → rows stored in useState
      → handlePost filters valid rows, dedups
      → calls postRateRequestBatch(lanes, userId)
      → service creates batch record
      → service creates lane records linked to batch
      → returns { batch, lanes, error }
      → component shows toast, clears grid

  This flow is correct but incomplete:
    - containerType and containerCount are captured in the UI
      but NOT passed through the service to the database
    - No navigation after success (user stays on empty grid)
    - No way to see what was just posted

  READ (nothing exists yet):

    No page fetches data from Supabase. Dashboard stats are
    hardcoded "—". My Requests is a placeholder. Received Rates
    is a placeholder. Provider pages are all placeholders.


────────────────────────────────────────────────────────────────────────────────
  WHAT THE DATA FLOW SHOULD BECOME
────────────────────────────────────────────────────────────────────────────────

  With React Query, the flow becomes:

  WRITE:
    NewRateRequest → useMutation (postBatch)
      → on success: invalidate ['batches'] query
      → navigate to /requester/requests
      → that page's useQuery(['batches']) auto-refetches

  READ:
    RequesterDashboard → useQuery(['stats', userId])
      → fetches counts from Supabase
      → returns { openRequests, pendingRates, ratesReceived }
      → stat cards render real numbers

    MyRequestsPage → useQuery(['batches', userId])
      → fetches batches + lane counts
      → renders list/table with status, dates, rate counts

    ReceivedRatesPage → useQuery(['rates', laneId])
      → fetches rates grouped by provider
      → renders comparison view

  This is the pattern. Each page declares what data it needs.
  React Query handles loading, errors, caching, refetching.


================================================================================
  PART 5: GAPS THAT WILL BITE YOU
================================================================================

  These are things that work fine today but will cause problems
  as the app grows. Ordered by when they'll hurt.


  1. SERVICE LAYER DOESN'T PASS NEW FIELDS (hurts NOW)

    rateRequestService.js line 39-43 maps lanes to:
      { batch_id, pol, fd }

    But NewRateRequest sends:
      { pol, fd, containerType, containerCount }

    containerType and containerCount are silently dropped.
    The database table also doesn't have these columns yet.
    When you create the Supabase tables, add the columns AND
    update the service mapping.


  2. NO DATA FETCHING PATTERN (hurts in Phase 2)

    The moment you build "My Requests" you need to fetch data.
    Without React Query (or at least a custom hook pattern),
    you'll write raw useEffect + useState for every page.
    Establish the pattern BEFORE building read pages.


  3. NO TOAST/NOTIFICATION SYSTEM (hurts in Phase 2)

    Toast is hardcoded in NewRateRequest. The next page that
    needs feedback (rate submitted, lane extended, error)
    will either duplicate the toast code or have no feedback.
    Extract it now.


  4. NO LOADING/ERROR STATES FOR DATA PAGES (hurts in Phase 2)

    PlaceholderPage handles "not built yet." Nothing handles
    "loading data" or "failed to load." Build generic Loading
    and ErrorState components before they're needed everywhere.


  5. DATAGRID COLUMNS NOT MEMOIZED (hurts with large CSVs)

    The columns array in NewRateRequest recreates on every render.
    With 500+ rows from CSV, DataGrid re-renders unnecessarily.
    Wrap in useMemo. Low effort, prevents future sluggishness.


  6. NO LANE DEDUP ACROSS BATCHES (hurts in production)

    dedup() in NewRateRequest checks for duplicates within the
    current grid. But it doesn't check against lanes already in
    the database. Your LANE_LIFECYCLE doc says "one active lane
    per POL + FD." This means the POST endpoint (or a pre-check
    query) must detect: "this lane already exists and is active."
    Without this, duplicate lanes WILL enter the database.


  7. 'dev-user' FALLBACK FOR requester_id (hurts on real DB)

    user?.id ?? 'dev-user' will fail on a UUID foreign key column.
    Either disable posting without auth, or use a valid dev UUID.


  8. NO CONFIRMATION BEFORE POSTING (hurts in production)

    Accidental batch posts to real freight forwarders. One
    window.confirm() or modal prevents this.

================================================================================
  SUMMARY
================================================================================

  The architecture is sound. Feature isolation, shared shell, role
  routing, and the service layer pattern are all correct and will
  scale.

  The main gap is the missing data fetching layer. Every page you
  build from here needs to read from Supabase, and doing that with
  raw useState/useEffect in every component will create unmaintainable
  boilerplate. React Query closes this gap with one dependency.

  The secondary gap is shared components. As you build more pages
  across both domains, you'll need toast, modals, badges, loading
  states, and error states. Without a shared layer, you'll duplicate
  code between requester and provider.

  Fix these two things and the project is ready to absorb Phase 2
  and Phase 3 features without structural changes.
