1. THE GOAL
________________________________________________________________________________

  Test the full two-role workflow with real people:
    - You (requester): create rate requests, post lanes
    - Your boss (provider): see open lanes, submit rates
    - Both have the same email domain (e.g., @primetimepackaging.com)

  Infrastructure:
    - DigitalOcean droplet serving the app
    - Cloudflare Tunnel exposing the droplet (no open ports)
    - Cloudflare Zero Trust controlling who can reach the app
    - Supabase handling auth, database, and role assignment


________________________________________________________________________________
2. HOW TO THINK ABOUT THE LAYERS
________________________________________________________________________________

  There are THREE separate layers of access control. Don't confuse them.

  LAYER 1 — CLOUDFLARE ZERO TRUST (who can reach the app at all)
  ──────────────────────────────────────────────────────────────
    This is a gate in front of your entire app.
    Before anyone sees a single pixel of your React app, Cloudflare
    checks: "Is this person allowed in?"

    For testing:
      Allow only two specific email addresses:
        - you@primetimepackaging.com
        - boss@primetimepackaging.com

    For production:
      Change the policy to allow anyone with @primetimepackaging.com
      (requester side) and specific freight forwarder emails you
      invite (provider side). Or open it wider if needed.

    What it controls: Network-level access. Who can load the website.
    What it does NOT control: What they can do inside the app.


  LAYER 2 — SUPABASE AUTH (who is logged in, what role they have)
  ──────────────────────────────────────────────────────────────
    Once someone passes Cloudflare, they land on your app and must
    log in via Supabase Auth (email/password, magic link, etc.).

    Supabase Auth gives each user:
      - A unique user ID (UUID)
      - User metadata (where you store their role)

    For testing:
      Hardcode roles for two users:
        - you@primetimepackaging.com  →  role: requester
        - boss@primetimepackaging.com →  role: provider

    For production:
      Role assignment based on how users are invited/onboarded
      (more on this in Section 5).

    What it controls: Identity and role. The app reads the role and
    shows the correct UI (requester dashboard vs provider dashboard).
    What it does NOT control: What data they can access in the database.


  LAYER 3 — SUPABASE RLS (what data each user can see/modify)
  ──────────────────────────────────────────────────────────────
    Row Level Security is database-level enforcement.
    Even if someone manipulates the browser JS client, RLS ensures
    they can only access rows they're authorized for.

    What it controls: Data access at the PostgreSQL level.

    More on whether you need this in Section 6.


  THE KEY INSIGHT:
    Cloudflare Zero Trust = bouncer at the door (who enters the building)
    Supabase Auth         = name badge (who you are inside)
    Supabase RLS          = locked filing cabinets (what data you can touch)

    Each layer is independent. You need all three eventually,
    but for testing you can start with just layers 1 and 2.

3. TESTING SETUP — STEP BY STEP
________________________________________________________________________________

  STEP 1 — Supabase Auth: Create two test accounts

    Option A (simplest): Create accounts manually in Supabase dashboard.
      Go to Authentication → Users → Add User.
      Create:
        Email: you@primetimepackaging.com    Password: (something)
        Email: boss@primetimepackaging.com   Password: (something)

    Option B: Let them sign up through the app (requires building a
    login page first).

    For testing, Option A is faster. You control both accounts.

  STEP 2 — Assign roles via user metadata

    In Supabase dashboard → Authentication → Users → click a user →
    edit user_metadata:

      For you:
        { "role": "requester", "full_name": "Luis" }

      For your boss:
        { "role": "provider", "full_name": "Boss Name" }

    Your AuthProvider already reads user.user_metadata.role — so the
    app will automatically show the correct interface for each login.

  STEP 3 — Build a minimal login page

    You need a login page so both of you can authenticate.
    It doesn't need to be fancy for testing:
      - Email input
      - Password input
      - Submit button that calls supabase.auth.signInWithPassword()
      - Error message if credentials are wrong
      - On success, AuthProvider picks up the session automatically

    No signup page needed for testing — you created accounts manually.

  STEP 4 — Cloudflare Tunnel setup

    On your DigitalOcean droplet:
      - Install cloudflared
      - Create a tunnel pointing to localhost:80 (where Nginx serves)
      - This gives you a URL like ratesapp.yourdomain.com routed
        through Cloudflare's network

    Your droplet has NO open ports. All traffic goes through the tunnel.

  STEP 5 — Cloudflare Zero Trust policy

    In Cloudflare Zero Trust dashboard → Access → Applications:
      - Add an application for your tunnel hostname
      - Create a policy:
          Name: "Test users only"
          Action: Allow
          Include: Emails
            - you@primetimepackaging.com
            - boss@primetimepackaging.com

    When anyone visits the URL, Cloudflare shows its own login screen
    first. Only these two emails get through to the app.

  STEP 6 — Test the flow

    You open the app:
      1. Cloudflare Zero Trust login (proves you're allowed in)
      2. App login page (Supabase auth — proves who you are)
      3. App loads → requester dashboard (because your role is requester)
      4. Create a rate request, post lanes

    Your boss opens the app:
      1. Cloudflare Zero Trust login
      2. App login page
      3. App loads → provider dashboard (because role is provider)
      4. Sees your posted lanes, submits rates

    You check your dashboard → rates received.
    That's the full loop.


________________________________________________________________________________
4. TWO LOGINS? (Cloudflare + Supabase)
________________________________________________________________________________

  Yes, during testing your users will log in twice:
    1. Cloudflare Zero Trust screen (email verification or one-time code)
    2. Your app's login page (Supabase email/password)

  This feels redundant but they serve different purposes:
    - Cloudflare: "Are you allowed to access this website at all?"
    - Supabase: "Who are you inside the app? What's your role?"

  For testing, this is fine. Both logins are quick.

  For production, you have options to reduce friction:
    - Cloudflare Access passes identity headers (Cf-Access-Jwt-Assertion)
      that your app could theoretically read to auto-login, but this
      requires server-side validation (Supabase Edge Function).
    - Or just accept the two logins — many B2B apps work this way.
      Cloudflare SSO is transparent after the first login (session cookie).

5. TRANSITIONING FROM TESTING TO PRODUCTION
________________________________________________________________________________

  TESTING (now):
    - 2 users, hardcoded in Supabase
    - Roles assigned manually via user_metadata
    - Cloudflare allows 2 specific emails

  PRODUCTION (later):

    REQUESTER SIDE (your company):
      Cloudflare Zero Trust policy:
        Include: Email domain → @primetimepackaging.com
      This lets any colleague with your domain access the app.

      Role assignment:
        Anyone signing up with @primetimepackaging.com automatically
        gets role: requester. You can do this with:
          - A Supabase database trigger that sets role based on email domain
          - Or a Supabase Edge Function that runs on auth.user_created event

    PROVIDER SIDE (freight forwarders):
      These are external companies. You won't know their email domains
      in advance. Options:

      Option A — Invite-based:
        You manually create provider accounts in Supabase and send them
        credentials. Safest, most controlled.

      Option B — Open signup with approval:
        Providers sign up, start with a "pending" role. You approve them
        and set role to "provider" in the dashboard.

      Option C — Domain allowlist:
        Maintain a list of approved provider email domains.
        Cloudflare policy: include these domains.
        Supabase trigger: assign provider role for those domains.

      For a rate request platform, Option A or B is typical.
      You want to control who can submit rates.

    THE TRANSITION:
      1. Change Cloudflare policy from "2 specific emails" to
         "domain @primetimepackaging.com + invited provider emails"
      2. Add a role-assignment trigger in Supabase (based on email domain)
      3. Build an admin view to manage provider accounts (optional,
         can do it from Supabase dashboard initially)
      4. Build a signup/invite flow for providers

    There's no big migration. You're just widening the same setup.

6. DO YOU NEED RLS? (honest answer)
________________________________________________________________________________

  SHORT ANSWER: Not yet for testing. Yes for production, but only on
  specific tables.

  HERE'S WHY:

  Without RLS, the Supabase anon key (which lives in your browser JS)
  can read and write ANY row in ANY table. The only thing protecting
  your data is your React code showing filtered views.

  But your React code runs in the browser. Anyone with browser dev
  tools can call supabase.from('rate_request_lanes').select('*') and
  see everything. Or worse, insert/update/delete rows they shouldn't.

  HOWEVER — your app sits behind Cloudflare Zero Trust. Only approved
  users can even reach the app. So the attack surface is tiny:
  only your own users could abuse it.

  FOR TESTING:
    Skip RLS. Use the permissive "allow all" policies. Focus on
    getting the workflow right. Two trusted users behind Zero Trust
    don't need database-level enforcement.

  FOR PRODUCTION — add RLS on these tables:

    rate_request_batches:
      - Requesters can read/write their own batches
      - Providers can read batches with status = 'posted' (open for quoting)

    rate_request_lanes:
      - Requesters can read/write lanes in their own batches
      - Providers can read lanes in posted batches

    provider_quotes (when you build it):
      - Providers can read/write their own quotes
      - Requesters can read quotes submitted to their lanes
      - Providers CANNOT see other providers' quotes
        ^^^ THIS is the real reason for RLS

  THE PROVIDER ISOLATION QUESTION:
    You mentioned "each forwarder can see rates provided by themselves."
    Yes, this is important and RLS is the right tool for it.

    Without RLS: Provider A could potentially see Provider B's rates
    by crafting a Supabase query in the browser console. Even behind
    Zero Trust, you don't want competing freight forwarders seeing
    each other's pricing.

    The RLS policy is simple:
      create policy "Providers see only their own quotes"
        on provider_quotes for select
        using (auth.uid() = provider_id);

    One line. Each provider only sees rows where they are the author.

  WHEN TO ADD IT:
    Add RLS when you build the provider_quotes table (Phase 3).
    That's when provider data isolation actually matters.
    Before that, there's only requester data and no competitive
    sensitivity.
